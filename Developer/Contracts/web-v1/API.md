# Pocket hosted web contract — web-v1 (agreed with Agent 2)

This supersedes the product direction of native v2. Existing v2 contract files remain legacy references. Pocket stores listing metadata and launches creator-hosted web interfaces; no UI JSON, downloaded native code, hosting or native-device bridge. Creators own website/API authentication and infrastructure. Listing sharing does not secure those websites/APIs.

## Manifest and registration
`schemaVersion: "web-v1"`, creatorKey (lowercase slug <=64), name (1..60), summary (1..160), entryURL, iconURL (absolute HTTPS <=2048; HTTP allowed only localhost/127.0.0.1/[::1] for development), version (1..32 text), optional appearance {colorScheme:"system"|"light"|"dark",themeColor:"#RRGGBB"}. No unknown keys. No whitespace-only text, credentials, backslashes or control/space characters in URLs; entryURL permits query/hash routing, iconURL no fragment. JSON <=8192 UTF-8 bytes. URLs are references, never server-fetched.

Account Bearer authentication uses existing /login. `POST /web-apps {manifest}` -> `{appId,revision,deepLink}`. Unique(owner,creatorKey); same appId across updates, revision starts 1/increments each success. deepLink is pocket://app/{server-appId}. `GET /web-apps/:id` -> `{appId,revision,manifest}` for owner/shared users. /apps lists kind:web and url:entryURL, plus optional manifest/revision/creatorKey. Existing POST /apps {name,url,summary} remains basic mode and its existing response; no creatorKey or notifications implied. Existing shares/deletes apply. Changing entryURL origin invalidates all app credentials, pairings, subscriptions, inbox entries; origin changes require fresh integration/consent. Same-origin path updates preserve these.

## Credentials and consent pairing
All endpoints below use account Bearer except two explicitly creator-authenticated endpoints. Credential scope is a server-issued appId, never arbitrary users. Only registered web-v1 apps support notifications.
- Owner `POST /apps/:id/notification-credential {}` -> `{appId,credential}`. Generate/rotate; raw credential returned once, only hash persisted. Old credential immediately invalid. Existing subscriptions survive rotation. Store it ONLY in creator backend environment/secret storage; never browser code, manifest, logs, MCP output or source control.
- In Pocket, user sees app name + origin and explicitly consents. `POST /apps/:id/pairings {consent:true}` -> `{pairingCode,expiresAt}` (Unix seconds, expires <=300s). Requires listing access; random >=128-bit single-use code scoped to consenting account and app. New pairing revokes previous outstanding codes for same app/user. No account token leaves Pocket. User copies code to creator app.
- Creator backend `POST /notification-pairings/redeem {pairingCode}` authenticated `Authorization: Bearer <app credential>` -> `{subscriptionId,appId,notificationsEnabled:true}`. Redeem atomically once before expiry and recheck listing access. Re-pair replaces old subscription for that app/account. Code is transferred in a body over HTTPS from browser to its own backend; never URL or logs. Creator binds returned opaque subscriptionId to its own authenticated user/session, not client-supplied recipient IDs. Browser only receives success status. No callback bridge required.
- Pocket `GET /notification-subscriptions` -> `{subscriptions:[{subscriptionId,appId,notificationsEnabled}]}` current account only.
- Pocket `POST /notification-subscriptions/:id/preferences {notificationsEnabled:boolean}` -> `{subscriptionId,appId,notificationsEnabled}`. Off rejects NEW events (409); no enqueue while muted. Existing inbox remains, OS notification permission is separately controlled and never implied.
- Pocket `DELETE /notification-subscriptions/:id` -> `{ok:true}`. Immediately invalidates subscription, pending codes and associated inbox entries. Removing listing access/deleting app also revokes associated pairing/subscription/inbox. Creator cannot enumerate subscriptions, account IDs or select arbitrary Pocket users.

## Events, inbox, exact launches
Creator backend `POST /notification-events` with app credential, body `{idempotencyKey,subscriptionId,title,body,target}` -> `{eventId,duplicate:boolean}`. idempotencyKey /^[A-Za-z0-9_-]{1,64}$/; subscriptionId opaque [A-Za-z0-9_-] <=128; title 1..80, body 1..240 (nonblank, no control chars); target <=2048. Request <=4096 bytes. One accepted event creates one inbox entry atomically. Unique(appId,idempotencyKey): identical retry returns same eventId, duplicate:true; different payload same key ->409. Auth/access/subscription validity checked before dedupe; a muted but otherwise-valid subscription may retry an already accepted event. Delivery confirmation means inbox acceptance, not APNs/device delivery. No APNs credentials or purchase required.

Target is origin-relative beginning one `/`, never `//`, a full URL or backslash. Query and hash supported. Reject raw whitespace/control, malformed percent escapes, encoded control/space/backslash, encoded slashes, and raw/encoded dot path segments; also reject encoded percent (%25) to avoid recursive decoding ambiguity. Resolve against REGISTERED entryURL origin (not entry path), verify origin unchanged. Inbox stores exact validated target, never trusts notification payload URLs. Retain targets verbatim including query/hash.

Pocket `GET /notification-inbox` -> `{entries:[{eventId,appId,title,body,target,createdAt,read}],nextCursor:null,unreadCount}` (default latest 100, Unix seconds). Only current authorized account. `POST /notification-inbox/:eventId/read {}` -> `{ok:true}`. `GET /notification-inbox/:eventId/launch` -> `{appId,target,url,deepLink}` rechecks current listing/subscription access; url=current registered origin+target, deepLink=`pocket://app/{appId}?event={eventId}`. Pocket resolves event ID through authorized backend before launching; push payload may contain eventId/appId only. No credentials in launch URL. OS push delivery is outside acceptance guarantees.

## Limits/errors/compatibility
All new request bodies <=16384 bytes except event <=4096, manifest <=8192. JSON objects only, unknown fields rejected, no NaN. New errors consistently `{error:"human readable"}`: 400 malformed/limits/unsafe target; 401 invalid/expired/mismatched auth kind; 403 owner-only credential operation; 404 missing/inaccessible app, subscription, inbox or invalid/expired/reused pairing; 409 disabled notifications or idempotency conflict; 429 rate limit if implemented. Do not echo credentials/codes in errors or logs. New endpoints must not accept account tokens as app credentials or app credentials as account tokens. IDs are opaque, never user supplied at registration. Fixtures use placeholder IDs/times/secrets for shape only. Old /apps HTTP(S) URL mode, login and share envelopes remain compatible; legacy v1 validation stays available. No automatic shared login or native behaviors for arbitrary sites.

### Agreed pagination, rate limits and delivery devices
`GET /notification-inbox?limit=100&before=<opaque cursor>&appId=<optional>`: limit1..100, default100, stable newest-first ordering. Response `{entries,nextCursor:string|null,unreadCount}`; unreadCount is total authorized unread (not just this page). Cursor is opaque and owner-scoped; invalid cursor ->400. Retain at most1000/account,30 days. Idempotency records retain30 days even if inbox entries are pruned; retries within that window return original receipt. Rates:60 new events/app/minute,20/subscription/minute;5 pairings/user/app/minute;10 credential rotations/app/hour. Limit ->429. Accepted retries bypass creation rates.

Owner `DELETE /apps/:id/notification-credential` -> `{ok:true}` revokes active credential and outstanding pairing codes, retains subscriptions. Rotation also invalidates outstanding codes.

Account `POST /notification-devices {deviceId:UUID,token:hex64..512,environment:"sandbox"|"production"}` -> `{ok:true,deliveryMode:"local"|"apns"}`. Bind device to current session/account, transfer ownership on registration. Account DELETE /notification-devices/:deviceId -> `{ok:true}`; logout deactivates that session's registrations. Tokens never returned/logged. Optional APNs transport may deliver only eventId/appId; local adapter must state local-only. Inbox remains authoritative regardless of OS permission/provider outcome. No browser push subscription or native bridge is defined here.
